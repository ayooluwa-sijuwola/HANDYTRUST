# Part 12 — Security Rules

Covers `firestore.rules` and `storage.rules`, both read directly and in full (multiple passes across this codebase's history, re-confirmed for this audit).

## Access-control helper functions (Firestore)
`isSignedIn()` (excludes anonymous auth explicitly — every privileged rule inherits this exclusion), `isOwner(uid)`, `isAdmin()` (existence check on `/admins/{uid}` — a Firestore doc, not a custom claim), `isArtisanEligible()` (approved + verified, reused across jobs/quotes), `isArtisanAccount()` (a cheaper existence-only check used for open-feed visibility), `isJobParty()`, `jobExists()`, `getJob()`. Field-diff scoping (`request.resource.data.diff(resource.data).affectedKeys().hasOnly([...])`) is used extensively to permit narrow, single-purpose partial updates without opening the whole document to arbitrary writes — this pattern is applied consistently across `agreedAmount`, `appointmentSlots`, `confirmedAppointment`, `progressStage`, and (newest) the three agreement-confirmation field groups.

## What each collection's rules protect (see Part 11 for the full collection list — this part focuses on the protection logic, not the schema)

- **`jobs`**: the core protection is `_isValidJobTransition()`, a full reimplementation of `JobService.allowedTransitions` in rules syntax — every status change is validated server-side independent of the client's `JobService` logic, so a compromised or modified client cannot force an illegal transition. Five additional narrow field-scoped rules permit specific non-status mutations (negotiated price, appointment slots/confirmation, progress stage, and — newest — the three agreement-confirmation actions) without opening the document broadly.
- **`jobs/{jobId}/messages`**: the pre-match multi-artisan exception (Part 9) is the most carefully-scoped rule in the file — read access for a not-yet-matched artisan is filtered to sender/receiver, not just job-adjacency, specifically to prevent one interested artisan reading another's private conversation with the same customer.
- **`jobs/{jobId}/quotes`**: doc-ID-equals-artisanId is itself a protection mechanism (Part 7) — it makes "one quote per artisan" a structural property rather than something rules have to separately enforce via a query.
- **`escrow_releases`**: client `create` is customer-only and client `update` is admin-only — but as documented in Part 8/11, the actual payout state machine is driven entirely by Cloud Functions via the Admin SDK, which bypasses these rules outright. The rules here protect against a malicious *client* forging or editing a release record; they provide no protection against a bug in the Cloud Function itself, which is a different trust boundary.
- **`admins`**: `allow write: if false` unconditionally is the strongest single line in the file — no client, including an existing admin, can ever grant or revoke admin status directly; it can only happen via Console/CLI or the two documented Cloud Function triggers.

## Weaknesses found, stated precisely

1. **`admin_alerts` has no rules block at all** (Part 11) — not a weak rule, an *absent* one. Under Firestore's default-deny posture this is safe (nothing can read it), but it means the collection is currently unusable by any client-facing admin feature without a rules change first — a gap between what Cloud Functions produce and what the app can consume.
2. **Two independent admin-authorization mechanisms, not automatically kept in sync.** Firestore rules' `isAdmin()` checks a Firestore document; `storage.rules`' `isAdmin()` (below) checks a custom Auth claim. `onAdminGranted`/`onAdminRevoked` sync the claim *from* the doc automatically, but this is a one-way, trigger-based sync with the usual custom-claim propagation delay (up to ~1h, or until the client's ID token is force-refreshed) — an account can be admin-by-Firestore-rules but not yet admin-by-Storage-rules for a window after being granted.
3. **Storage read rules are broader than the Firestore rules protecting the same content**, confirmed by direct reading of `storage.rules`:
   - `/jobs/{jobId}/{uid}/**` (job photos): `allow read: if isSignedIn()` — any authenticated user, not scoped to job parties, even though the corresponding Firestore `jobs` document is properly party-scoped. Plausibly deliberate for the open-feed browsing case (an artisan considering a job should see its photos pre-quote), but the broad read persists after the job is matched/completed too, with no narrowing.
   - `/disputes/{disputeId}/{uid}/**` (dispute evidence): same `isSignedIn()` breadth, with **no comparable justification** — the corresponding Firestore `disputes` doc is correctly restricted to the raiser/against-party/admin, but the evidence photos attached to it are readable by any signed-in stranger. This is the more serious of the two findings; evidence photos can plausibly contain sensitive content (a person's living space, injury photos, a document photographed as evidence).
4. **`config`'s read rule is broad relative to what it could theoretically hold.** `allow read: if isSignedIn()` on the whole collection, with no structural separation between "safe to expose" fields (a Paystack *public* key) and anything that could become sensitive later. The client code that once read a secret from here has been replaced with a Cloud-Functions-only path, but the rule itself still permits any signed-in user to read whatever is written to any document in this collection.
5. **Verification-status self-escalation is narrowly bounded but worth naming**: an artisan's own `verificationStatus` field is owner-writable only among `unverified`/`id_submitted`/`pending_later` — they cannot self-promote to `id_verified`/`trusted` (only admin approval can), which is correct, but it's worth stating explicitly that this is the one field on the `artisans` document where the owner has *any* write access to a status-like value at all, given every other status-bearing field (`approvalStatus`, `trustScore`, rating aggregates, dispute counts) is entirely server/admin-managed.

## Rules that do not match the client code exactly

- No case was found in this pass where a client code path attempts a write the rules would silently allow beyond what the UI intends (the opposite direction — client code correctly gated by UI logic that rules then double-enforce — is the pattern found throughout, e.g. the agreement-confirmation gate on `paymentPending`). The one genuine mismatch identified was corrected during this audit itself (Part 6): an earlier draft of this documentation incorrectly asserted a rules/comment discrepancy on dispute-raising that, on direct verification, does not exist — both the `jobs` transition rule and the separate `disputes` collection's own `create` rule agree the action is customer-only.
- **Storage vs. Firestore scope mismatches** (point 3 above) are the one confirmed, real instance of "rules not matching the intent of the code they're meant to protect" — the Firestore side is correctly scoped, the Storage side protecting the same logical content is not.

## `storage.rules` — full structure
`isSignedIn()` (same anonymous-exclusion pattern as Firestore), `isOwner(uid)`, `isAdmin()` (custom-claim-based, per point 2 above). Five path patterns: `/jobs/{jobId}/{uid}/**`, `/users/{uid}/**` (profile photos — broad read is correct here, these are meant to be public avatars), `/artisan_portfolio/{uid}/**` (broad read correct — portfolios are meant to be public), `/verifications/{uid}/**` (owner/admin read only — correctly the tightest read rule in the file, matching the sensitivity of ID documents), `/disputes/{disputeId}/{uid}/**` (see weakness 3). Every write path enforces file-size limits (5MB general, 10MB for verification docs) and a `contentType.matches('image/.*')` check — no non-image upload is possible through any of these paths.
