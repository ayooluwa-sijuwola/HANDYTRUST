# 01.5 — Independent Critical Review of the Phase 1 Audit, and Hardening Sprint Plan

Role: independent second-pass review of `01-ux-audit.md`, performed by re-verifying its highest-stakes claims directly against source rather than trusting the audit's own citations. Two findings did not survive that check and have been corrected in `01-ux-audit.md` directly (marked with strikethrough + errata notes there). This document is the record of that review, the corrected prioritization, and the resulting sprint plan.

---

## 1. Were any findings wrong, exaggerated, or missing context?

### Wrong — retracted

**Finding 1.4 ("auto-release escrow function is deployed-but-broken / missing composite index") is false.** I read `firestore.indexes.json` directly: lines 37-44 declare exactly `jobs: status ASC, autoReleaseAt ASC` — precisely the index `autoReleaseEscrow`'s query (`status == 'submitted' AND autoReleaseAt <= now`, `functions/index.js:108-112`) needs. The original claim traced back to a line in `README.md`'s "Known Limitations" section that was never independently checked against the actual index file. That's a real methodology failure in the Phase 1 audit — a specific, mechanically checkable claim ("this index doesn't exist") got repeated from a secondary source instead of the primary one. It's now retracted from Critical and replaced with the much smaller, real residual issue: no confirmation the declared index is actually *built* in the live Firebase project, and no alerting on scheduled-function failures generally.

### Exaggerated — downgraded

**Finding 1.2 ("Paystack secret key is exposed to every signed-in user") overstated present-tense risk.** I read `paystack_service.dart` directly: its own doc comment states the vulnerable direct-Paystack-call-with-Firestore-sourced-secret design is describing the **past** — "Previously this class called the Paystack REST API directly... The secret key never reaches the client now." I also read `firestore.rules:399-402`: `/config/{doc}` has `write: if false`, so no client, malicious or otherwise, can plant a secret there. The vulnerability, as a live, exploitable path, does not currently exist. What's real and worth keeping is a much smaller point: `/config` still allows broad `read: if isSignedIn()` with no structural distinction between "safe to expose" and "sensitive" fields, so the *pattern* has no guardrail against a future regression (e.g., someone manually adding a secret to that doc via the console during an incident and forgetting to lock read access down). That's a hardening item, not an active breach. Downgraded to Medium (tracked as 3.7 in the audit).

### Narrowed — real, but smaller than stated

**Finding 2.3 (dual escrow state-machine implementations, "48h vs 7 days disagreement")** is directionally correct but overstated its blast radius. I grepped every call site of `EscrowService` — it's used **only** by `demo_payment_provider.dart`. Production payment goes through `JobService` exclusively, which is internally consistent (its own code comment documents that the 7-day-vs-48h discrepancy was previously found and fixed on the `JobService` side). So this isn't "a real customer could get either window" — it's "the demo flow has quietly stale logic relative to production," which only matters in combination with 2.2 (the demo path being reachable, ungated, from production UI). Narrowed and re-sequenced as dependent on 2.2 rather than independently urgent.

### Findings that held up under scrutiny

- **1.1 (escrow payout automation missing)** — confirmed by direct grep: zero references to `escrow_releases` anywhere in `functions/index.js`. No consuming function exists. This is real, and it's the most consequential finding in the whole audit.
- **1.3 (Trust Score doesn't drive ranking; three separate scoring formulas exist)** — confirmed by reading `matching_service.dart` and `artisan_model.dart` directly. `_score()` uses `ArtisanModel.matchScore` (a third formula: rating 40% + completionRate 30% + responseTime 20%) plus a distance bonus. `trustScore` (the real, server-computed, Cloud-Functions-authoritative score) is never read by the matching path. This is real and, if anything, the audit undersold it slightly — it didn't emphasize enough that this is a *marketing/trust-claim* risk as much as a ranking-quality one: if this were ever surfaced publicly ("we rank by trust score") it would be a false claim about a live product.

### Missing context the original audit should have included

- **No evidence this app has real production traffic yet.** The audit writes about 1.1 as if artisans are actively being stiffed right now. More likely framing: this is a pre-launch/limited-testing product (no test suite, no CI, self-documented incomplete payout path — these are pre-launch signals, not signs of an app already live with paying customers). That changes urgency framing from "stop the bleeding" to "this blocks launch, full stop" — which is arguably *more* actionable, not less, because it's a hard gate rather than an incident to firefight. I'm making this explicit rather than leaving it ambiguous.
- **The audit didn't distinguish "structurally broken" from "incomplete but consistent."** 1.1 and 1.3 are the former — the code that exists is internally consistent, it's just missing a piece or wired to the wrong input. That's a much better place to be than contradictory logic in production. Worth saying plainly: this codebase is in better shape than the "4 critical findings" framing implies at first read. Two of those four weren't real.

## 2. Reprioritization

Scored across four axes, 1 (low) – 5 (high). "Engineering dependency" is inverted for ranking purposes — lower dependency/complexity means faster to ship, which matters for sequencing even when trust/financial impact is high.

| Item | User trust impact | Financial risk | Eng. complexity | Business value | Net priority |
|---|---|---|---|---|---|
| **Escrow payout automation (1.1)** | 5 — artisans not getting paid is existential for supply-side trust in a 2-sided market | 5 — this is literally "does money move correctly" | 4 (new Paystack Transfer integration, recipient codes, retry/reconciliation, failure UX) | 5 — without this, there is no viable marketplace | **P0, biggest lift** |
| **Trust Score → ranking (1.3)** | 5 — the product's entire differentiation claim is unmet | 2 — doesn't move money, but misroutes demand toward lower-trust supply | 2 (mostly a `matching_service.dart` rewrite; `trustScore` index already exists as a field override) | 4 — core differentiator vs. informal/cash marketplaces | **P0, cheapest fix relative to impact** |
| **Un-gate demo payment path + delete/replace `EscrowService` (2.2 + 2.3)** | 3 — low probability but high embarrassment if a real user reaches a fake payment screen | 3 — same reason | 2 (build-flag gate + one deletion) | 2 | **P0, trivial cost** |
| **Config rules hardening (3.7)** | 1 — no live exposure today | 2 — pure defense-in-depth against a future mistake | 1 | 1 | **P1, do it because it's nearly free** |
| **Scheduled-function monitoring/alerting (3.8)** | 2 — invisible failures erode trust once discovered | 3 — money-adjacent (escrow timing) | 2 | 2 | **P1** |
| **Rate limiting / App Check (2.7)** | 3 — protects against spam/abuse degrading trust | 2 | 3 (App Check rollout across platforms + Cloud Function counters) | 2 | **P1, before any public/marketing push** |
| **Trust Score gaming vectors — new-account default, review farming (2.4, 2.6)** | 4 — directly undermines the score once ranking depends on it (1.3) | 2 | 3 (Bayesian rating shrinkage, anomaly surfacing) | 3 | **P1, sequenced right after 1.3 — no point hardening a score nothing reads yet** |
| **Role-unaware FAB (2.1)** | 2 | 1 | 1 | 2 | **P2 — cheap, do it, but not urgent** |
| **"Verify Later" messaging gap (2.8)** | 2 | 1 | 2 | 2 | **P2** |

**What moved most from the original audit's ordering**: Trust Score ranking (1.3) moves *up* relative to escrow payout in "speed to value" terms — it's a much smaller engineering lift for a very large trust-claim fix, so it shouldn't be sequenced strictly after the much larger payout build. They can and should run in parallel (different engineers, different systems: one is Flutter+Cloud-Functions matching logic, the other is a new Paystack Transfer integration). The original audit's flat numbered list (1→2→3→4) implied strict sequencing that isn't actually necessary or optimal.

## 3. Proceed to Phase 2, fix backend first, or another approach?

**Recommendation: a modified (B) — fix the true P0s in a scoped hardening sprint, but run design-system foundation work (Phase 2) in parallel, not after.**

Reasoning:
- Shipping a beautiful redesigned UI on top of an escrow system that doesn't pay artisans is negative-value work — it makes the product *more* convincing to onboard real artisans into a flow that currently fails them financially. That's the strongest argument for not simply proceeding to (A).
- But (B) taken literally — "fix everything backend before any design work" — wastes the fact that design-system work (tokens, typography, component library) has **zero dependency** on the escrow/ranking fixes and is needed regardless of how those land. It's a different engineering surface (Flutter theming, not Cloud Functions/Firestore) and can be built by a different track of work without contention.
- What genuinely should wait is **Phase 9 (screen-by-screen redesign)** and **Phase 10 (admin redesign)** — those specs would need to describe wallet screens, milestone payment UI, and GPS/ETA flows that don't exist yet and whose shape depends on decisions made while building the hardening items (e.g., how payout failures surface to the artisan directly affects what the wallet screen needs to show).

So, concretely: **run the Phase 1.5 hardening sprint below and Phase 2 (design system) concurrently now; hold Phase 9/10 until the hardening sprint's P0 items are at least architecturally decided (not necessarily fully shipped) so the screen specs aren't designed against a moving target.**

(C) is not needed — there isn't a third path here better than "parallelize the independent tracks, sequence the dependent ones."

## 4. Phase 1.5 — Hardening Sprint

### Goals
1. Make the escrow promise true end-to-end: money that gets locked, gets paid out.
2. Make the Trust Score claim true: the score that's computed is the score that ranks.
3. Close the two cheap, high-leverage safety gaps (demo-path gating, config rules) before any wider audience touches the app.
4. Do this without touching visual design, without adding new product surface (no milestone payments, no wallet UI, no GPS yet) — this sprint is about making existing promises true, not building new ones.

### Tasks

**Track A — Escrow payout automation (owns 1.1)**
- A1. Design the payout state machine: `escrow_releases.status`: `pending → processing → completed | failed`, with a `failureReason` field and a retry counter.
- A2. Cloud Function (Firestore-triggered on `escrow_releases` creation, or a scheduled sweeper for resilience against a missed trigger) that: validates the artisan has bank details in `artisan_private/{uid}`, creates/reuses a Paystack Transfer Recipient, initiates a Paystack Transfer, and writes the result back.
- A3. Paystack Transfer webhook handler (mirrors the existing `paystackWebhook` pattern for charges) to catch async transfer success/failure and update the release doc authoritatively — do not trust only the synchronous initiate-call response, the existing charge-webhook pattern in this codebase already establishes why (webhook is the source of truth, not the client-facing call).
- A4. Failure path: if an artisan has no bank details or the transfer fails, the job/escrow must **not** silently sit in limbo — surface this to the artisan (fix bank details) and to an admin queue (manual intervention path) rather than a Firestore doc nobody looks at.
- A5. Reconciliation: a daily scheduled function or admin-triggered report comparing `escrow_releases` in `pending`/`processing` beyond an SLA window (e.g., >24h) against Paystack's transfer list, surfaced to the admin Escrow Monitoring section (still exists only as a concept — the minimum viable version here is a Firestore query + admin alert, not a new screen).

**Track B — Trust Score → ranking (owns 1.3)**
- B1. Decide the single canonical scoring output for ranking: use the existing server-authoritative `artisans.trustScore` field directly — do not invent a fourth formula. Retire `ArtisanModel.matchScore` as a ranking input (it can stay as a display concept if genuinely useful, but must stop being what `_score()` sorts by).
- B2. Rewrite `MatchingService._rank`/`_score` so the sort key is **(distance bucket, trustScore, rating, completedJobs)** in that priority order, matching the brief exactly — distance as a coarse primary bucket (e.g., within 5km / 15km / 50km rings) rather than a continuous tiebreaker-only bonus, since the brief specifies distance as the *first* priority, not a minor adjustment.
- B3. Confirm the existing `artisans.trustScore` field-override index (already present in `firestore.indexes.json`, both ascending/descending) supports the new query shape; add any additional composite index the new sort actually needs (e.g., `category + approvalStatus + trustScore` already exists — verify it covers the distance-bucketed query pattern once B2 is designed, since bucketing distance likely means an additional `where` clause).
- B4. Do **not** yet build the Bayesian-rating-shrinkage fix (2.4) or review-farming detection (2.6) in this sprint — sequence them immediately after, once ranking actually depends on the score (no point hardening an input nothing reads yet, per the reprioritization above).

**Track C — Cheap, high-leverage safety (owns 2.2, 2.3, 3.7, 3.8)**
- C1. Gate `DemoEscrowScreen`/demo payment route behind a build-time flag (`kDebugMode` or a dedicated `--dart-define`); confirm it is unreachable in a release build via a manual release-build smoke test, not just code inspection.
- C2. Delete `EscrowService` once C1 lands (or the demo path is rebuilt on top of `JobService` directly) — do not leave two implementations sitting side by side.
- C3. Split `/config` into a genuinely-public document (Paystack public key, feature flags) with broad read, and remove the general-purpose broad-read pattern for anything that could plausibly become sensitive later. Cheap rules change, ships same day.
- C4. Confirm the `jobs: status+autoReleaseAt` index is actually **built** (not just declared) in the live Firebase project console. Add a Cloud Monitoring alert policy on error count for `autoReleaseEscrow` and the new payout function from Track A.

### Dependencies
- A3 (transfer webhook) depends on A2 (initiate function) existing first, same pattern as the existing charge webhook.
- A4/A5 depend on A1's state machine being decided before either is built against it.
- B2 depends on B1's decision (which field is canonical) being made and communicated — this is a product decision as much as an engineering one (confirm with product/you before code: is it truly `trustScore` unmodified, or `trustScore` with the 2.4 dampening applied later as a second pass?).
- C2 depends on C1 shipping first (don't delete the fallback until the replacement gate is confirmed working).
- Track A and Track B have no dependency on each other and should run in parallel if there are two engineering tracks available; if there's only one, **Track B ships first** (much smaller, de-risks the "is trust score even right" question before the bigger payout build) with Track C's C1/C3 interleaved as near-zero-cost quick wins.

### Expected outcomes
- A real job, completed and confirmed, results in an actual Paystack transfer to the artisan's bank account, with a visible failure path if it doesn't — verifiable end-to-end in a staging environment with Paystack test-mode transfers.
- Two artisans with identical distance from a customer rank by trust score first, not by the current three-formula mishmash — verifiable by a unit test on `MatchingService._rank` with fixture data.
- The demo payment screen is unreachable in a release build — verifiable by attempting to navigate to its route in a release build and confirming a 404/redirect.
- `/config` no longer has a plausible path to ever leak a secret, structurally, not just by convention.
- A killed/failing scheduled function produces an alert instead of silence.

### What should NOT be built yet
- Milestone/material payments, refund workflow, wallet screen (Phase 6 territory — needs its own spec; bolting milestones onto the current single-lock escrow mid-hardening-sprint would be scope creep into a redesign phase this sprint isn't chartered for).
- Live GPS "I'm on my way" tracking (Phase 7 — needs a map dependency decision first, unrelated to hardening).
- Notification preferences screen, chat search/archive, voice notes (Phase 8 — net-new UX, not integrity-fixing).
- Bayesian trust-score rating shrinkage and review-farming anomaly detection (2.4/2.6) — real, but explicitly sequenced *after* this sprint per Track B's B4 note; building them before ranking depends on the score is wasted precision.
- Any visual/UI redesign work beyond what's structurally required by C1 (a build flag needs no new UI) — Phase 2 (design system) proceeds separately and does not touch these tracks.
- Full admin Escrow Monitoring dashboard — A5's minimum viable version is a query + alert; a real dashboard section belongs in Phase 10.

## 5. Do escrow payout, auto-release reliability, and Trust Score ranking deserve P0?

- **Escrow payout automation — yes, unambiguously P0.** It's not a UX gap, it's a missing half of the core transaction. No reprioritization axis argues against this; the only question was ever sequencing relative to Trust Score, not whether it's P0.
- **Escrow auto-release *reliability* — P0 only if reframed correctly.** As literally stated in the original audit ("missing index, silently broken"), it wasn't P0 because it wasn't true — the index exists. The *actual* residual gap (no confirmation the index is live-built, no monitoring) is real but is a P1-scale operational hardening task, not a P0 correctness bug. I'd resist calling it P0 under its original description — that would mean fixing something that isn't broken while a monitoring gap goes under-resourced because it's badge-labeled the same as "artisans aren't getting paid."
- **Trust Score → ranking — yes, P0, and cheaper than it looks.** The engineering lift is genuinely small (one service's ranking function, an already-existing index), and the trust/business-value impact is large. This is close to the best cost/impact ratio in the entire audit — it should not be scheduled behind the much larger escrow payout build; run them in parallel.

## 6. Recommended roadmap order, audit → production-ready

1. **Phase 1.5 Hardening Sprint** (this document) — Tracks B and C first/fast, Track A in parallel or immediately after depending on team size. This is the launch gate; nothing after this point should be marketed as "trust-based" or "escrow-protected" until Track A and B ship.
2. **Phase 2 — Design System**, run concurrently with #1 (different engineering surface, no shared dependency). Ends with a confirmed, documented token/component set — including resolving the admin-dashboard color-system split (`AdminPalette` vs `AppColors`) flagged in the audit's 3.3.
3. **Phase 5 — Trust Score algorithm spec**, immediately after Track B ships, to formally design the 2.4/2.6 hardening (rating shrinkage, review-farming signals) now that ranking actually depends on the score. This is a natural sequel to Track B, not a parallel track — it needs Track B's decisions as a starting point.
4. **Phase 4 — Firestore architecture doc**, incorporating the config-rules split (3.7), rate-limiting/App Check design (2.7), and any new collections Track A's payout state machine introduced (`escrow_releases` schema, formalized).
5. **Phase 6 — Escrow & Wallet flow spec**, now free to design milestone/material payments, refund workflow, and a real wallet screen on top of a payout system that actually works (Track A) — sequencing this before Track A ships would mean designing UI for a backend that doesn't exist yet.
6. **Phase 7 — GPS flow spec**, independent of the above; can be pulled earlier if there's spare capacity, since it has no dependency on Tracks A/B/C.
7. **Phase 8 — Messaging & Notifications spec**, similarly independent; the audit's missing-features table (appointment/escrow/review reminders, chat archive/search) has no hard dependency on the hardening sprint.
8. **Phase 3 — IA, navigation & journeys**, once the shape of new flows (wallet, GPS, milestone payments) is spec'd in 5-7, so navigation is designed against the real future surface area, not guessed at.
9. **Phase 9 — Screen-by-screen redesign (customer/artisan)**, now that every underlying flow it depends on (escrow, trust score, GPS, messaging, IA) has a settled spec.
10. **Phase 10 — Admin web + mobile redesign**, last among the design phases — admin surfaces need to reflect the finished escrow monitoring, trust score management, and dispute flows from everything above.
11. **Phase 11 — Production readiness checklist, missing-features backlog, roadmap** — becomes the closing synthesis document once 1-10 exist, rather than a guess made before the real gaps were known.

This differs from the original 00-overview.md's straight 1→11 numbering mainly in making the parallelism explicit (2 runs alongside 1; 6/7/8 don't block each other) and inserting this hardening sprint before the phases whose specs would otherwise be written against a backend that doesn't yet do what the product claims.
