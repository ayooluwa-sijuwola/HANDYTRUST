## CONFIRMED LIVE — working correctly

1. **Register screen client-side validation** — empty-field submit shows inline errors ("Enter your full name", "Email is required", "Password must be at least 8 characters") without navigating away or crashing. Screenshot: register_02_empty_validation.png.
2. **Register screen invalid-input validation** — malformed email ("not-an-email") and weak password ("weak") both correctly blocked with inline errors before any network call. Screenshot: register_03_invalid_validation.png.
3. **Successful customer signup** — valid data submits, creates a real Firebase Auth user, redirects to a well-designed Verify Email screen ("Resend verification email" / "I've verified — continue" / "Use a different account"). Confirms register_screen.dart -> auth_provider.dart -> router redirect chain works end-to-end live.
4. **Successful artisan signup** — same flow with Artisan role selected works identically.
5. **Duplicate email signup** — re-registering an already-used email shows the clean, friendly SnackBar "An account with this email already exists." — NOT a raw Firebase error code. Screenshot: edge_02_duplicate_email.png.
6. **Wrong-password login** — shows "Email or password is incorrect." — clean, and notably does NOT distinguish wrong-password from non-existent-account (see next item), which is good security practice (doesn't leak account existence).
7. **Non-existent-account login** — shows the identical "Email or password is incorrect." message as wrong-password. Confirms auth_service.dart::friendlyError intentionally/effectively unifies these Firebase error codes into one message.
8. **Forgot-password flow, happy path** — entering a valid registered email and clicking "Send Reset Link" transitions to "Check your inbox — We sent a password reset link to {email}" with a "Back to Login" button. Matches code prediction exactly.
   - **NOTE on the P0 finding from the code-level error-handling audit** (forgot_password_screen.dart / auth_provider.dart swallowing FirebaseAuthException without rethrow): the happy-path mechanism was confirmed live to work exactly as the code describes — the screen transitions to "success" purely based on the awaited call not throwing an *uncaught* exception, with no check of provider error state. I was NOT able to force a live `too-many-requests`/rate-limit response in this session (the UI navigates away after the first successful send, removing the retry button, so re-triggering the send action requires navigating back to the form each time — I did not spend the ~15-20 round trips against production Firebase Auth's real rate limiter needed to attempt this, to avoid unnecessary load/abuse-flagging on the real project). **Verdict: CODE-LEVEL CONFIRMED (unambiguous swallow-without-rethrow pattern), mechanism partially LIVE VERIFIED (success-screen trigger condition confirmed), the specific false-success-under-real-error scenario is UNABLE TO VERIFY live without deliberately hammering production auth.**
9. **Session persistence across hard refresh** — logged in as the (deliberately still-unverified) artisan account, hard-refreshed the page: correctly remained on /verify-email (did not bounce to /login or lose session). Confirms Firebase Auth persistence + router redirect logic work together correctly on Flutter Web.

## Minor observations (not bugs, informational)
- On the login/register screens, the accessible name (`aria-label`) exposed for the Email/Password `<input>` elements is the **hint text** (e.g. "name@company.com", "••••••••"), not the visible field label ("Email Address", "Password"). A screen reader would announce the hint placeholder as the field's name rather than its label. This is a minor accessibility (WCAG) nit, not part of this audit's core scope, but worth a footnote — **P3, accessibility polish**.
